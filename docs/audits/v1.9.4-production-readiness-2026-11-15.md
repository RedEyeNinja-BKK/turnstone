# Turnstone Production Readiness Audit — v1.9.4

**Audit date:** 2026-11-15
**Auditor:** automated read-only inspection of the production host and both Git remotes
**Classification:** **B — ALIGNMENT REQUIRED**
**Scope:** read-only. No production component was modified, restarted, migrated or reconfigured.

---

## 1. Executive summary

Production runs **Turnstone 1.8.7** (five `turnstone-server` processes — one head plus four
execution nodes — plus a console and a Discord channel gateway), installed as a **pip wheel** in
`/opt/turnstone-venv` (Python 3.13.5), with a **25-file overlay** applied through `PYTHONPATH`.
The overlay is a *complete package copy*: while the drop-in exists, nothing is imported from the
base install.

The overlay is **not any single Git commit**. It is a three-layer stack built locally on the host:

| Layer | Origin | Evidence |
|---|---|---|
| Sensor + typed-decision + OAuth-store modules | unmerged fork branch `integration/s6-runtime-v187-5427ded` | 7-file delta vs live |
| Judge-abandonment audit (PR #20) | `fix/judge-cancel-reason-accounting`, merged to fork `main` | deploy receipt `pr20-judge-audit-20261111T073729Z.txt` |
| Console model-form round-trip (PR #21) | `fix/console-model-form-roundtrip`, merged to fork `main` | deploy receipt `pr21-console-form-20261111T083404Z.txt` |

**No fork branch declares version 1.8.7** (the highest is `1.8.0a7`), and no branch contains the
deployed overlay as a tree. Production provenance is therefore **host-local and not reproducible
from GitHub alone**.

Upgrading to v1.9.4 is **not** a manual-update case. Four independent blockers each require
staging work before a cutover could be attempted:

1. **The overlay must be re-based onto 1.9.4.** `core/session.py` alone differs by ~8,300 lines
   between the live overlay and v1.9.4, and v1.9.0 *removed* `ChatSession.resume()`, which the
   overlay still defines and calls.
2. **The MCP Python SDK major version is a hard break.** v1.9.4 requires `mcp>=2.3,<3`; every
   custom MCP server imports `mcp.server.fastmcp.FastMCP`, which **raises `ModuleNotFoundError`
   by design in mcp 2.x** (renamed `MCPServer`). All nine registered MCP servers would fail.
3. **Dependency floors move across majors:** `anthropic 0.125.0 → >=2,<3`,
   `mcp 1.30.0 → >=2.3,<3`, `openai 3.13.0 → >=3.14.1`. The venv cannot be updated in place
   without rebuilding every consumer.
4. **Database migration lineage needs validation.** Production sits at revision **076** — exactly
   the stock 1.8.7 head — so the path to 088 is linear and *appears* clean, but it crosses
   destructive migration 080 and must be rehearsed against a disposable copy first.

A manual upgrade command block **cannot be safely issued today**. The recommended path is a staged
alignment (Section 9).

### 2.9 Backup and recovery

`turnstone-backup.service` runs nightly at 03:15 from `/usr/local/sbin/turnstone-backup` as root,
under `flock`, with fail-closed exit codes. It:

1. verifies every required source path exists,
2. verifies the TrueNAS mount is a real `nfs4` mount (automount-aware guard),
3. takes a `pg_dump`,
4. writes an encrypted restic snapshot to the NFS repo,
5. verifies the new snapshot actually contains the PostgreSQL dump,
6. **never prunes or deletes**.

The restic repository is live and was written today (index and snapshot directories updated
2026-11-15 03:15). The last several `pg_dump` files are present and dated daily through 2026-10-30
in the local rolling directory. The backup log is root-only (0600) and was **not readable** by the
audit account — its contents are unverified (see §8.4).

### 3.3 Provenance ambiguity (material)

- **No fork branch declares version 1.8.7.** Distinct `pyproject.toml` versions across all 52 remote
  branches: `1.8.0a7` (22), `1.8.4` (12), `1.8.5` (4), `1.8.3` (3), `1.8.0a5` (3), `1.8.0` (3),
  `1.8.0a6+localclaw…` (1). The deployed version exists **only on this host**.
- The overlay directories carry **no manifest, no git metadata and no build receipt** — only the
  package tree.
- `production/current` (1.8.4) and `production/deployed-lineage` (1.8.0) are both **older** than the
  deployed 1.8.7 and do **not** contain the sensor, typed-decision or validation-corpus modules.
  Neither branch identifies the deployed runtime.
- The sensor lineage was **deployed but never merged to fork `main`**: `5427ded` and `6aa6bd07` are
  not ancestors of `origin/main`, and `origin/main` contains **no** `sensor_lifecycle.py`,
  `shadow_driver.py`, `typed_decision.py` or `validation_corpus.py`.
- The overlay SHAs embedded in slot names (`4254d14f`, `3d2f0b61`) are **not** commit IDs in either
  repository — they are build/asset digests (the PR #21 one is an asset SHA-256 prefix).

**Conclusion:** the exact source commit of the deployed runtime **cannot be proven**. What *can* be
proven is the file-level delta against both the 1.8.7 wheel and `6aa6bd07`, which is a complete and
sufficient specification for re-creating the overlay.

### 7.3 MCP SDK v2 — the hard blocker

Verified by inspecting the `mcp==2.3.0` wheel directly:

```
mcp/server/fastmcp.py  (16 lines)
  """Removed in mcp 2: `FastMCP` is now `mcp.server.mcpserver.MCPServer`. ..."""
  raise ModuleNotFoundError(_MESSAGE, name=__name__)
```

`FastMCP` **does not exist** in mcp 2.x — importing it raises `ModuleNotFoundError` with a migration
message. Also renamed/changed: `McpError`→`MCPError`, `streamablehttp_client`→
`streamable_http_client`, and the client now builds per-connection `httpx2` clients.

**Impact:** all six custom MCP servers (Section 5.7) must be ported to `MCPServer`. The
`dockhand-expert` and `switchyard-ops` / `openclaw-admin` servers run from the **same venv** as
`turnstone-server`, so upgrading the venv in place breaks them immediately.

`TransportSecuritySettings` still exists in `mcp/server/transport_security.py` (used by the dockhand
and truenas HTTP runtimes), so that specific API is safe.

### 7.4 Session / storage interface changes

v1.9.0 removed `ChatSession.resume()` and replaced it with `SessionManager.open()` +
`rehydrate()`. Custom session hosts and storage backends must:

- pass `workstream_lease` into the session factory,
- support lease acquisition, renewal, release and fenced writes,
- implement `list_saved_workstreams` and the revised history/timestamp contracts,
- start a lease keeper and release leases at shutdown.

The live overlay defines `resume()` (`session.py:7090`) and has **no** `workstream_lease.py` and **no**
lease support. Any custom factory or subclass in the overlay is affected.

### 7.5 Coordinator behavior

v1.9.x changes coordinator interruption (immediate on user message), parallel child spawning,
`evaluation` state (new, must be added to any state enumeration), and removes the coordinator
capacity cap (migration 087). The live overlay's `console/coordinator_*.py` and CLI cluster views
enumerate states and would need the new `evaluation` state.

### 7.6 Model selection and judge configuration

- `[model].fallback` is **ignored** with a warning (v1.9.0 removal). Custom registry integrations must
  drop their `fallback` argument.
- `judge.output_guard_model` now falls back to `judge.model`, then the session model.
- v1.9.4 adds `tools.web_fetch_alias`; with it unset, a task agent's `web_fetch` uses the task
  agent's model.
- Skills lose model settings (migration 080) — see §6.3.

The live registry has 84 enabled models (81 `openai-compatible`, 3 `openai`). Endpoint hosts break down
as: two tailnet GPU appliance hosts (6 and 4 aliases respectively, one on `https`, one on `http`),
the internal model router, and three public providers (OpenRouter, DeepSeek, OpenAI). **No private CA
is installed** (148 public roots in the system bundle), so the trust-store change is expected to be
benign — the tailnet appliance certificates are ordinary public-CA or self-signed and would need
verification at cutover; the two `http://` lanes are unaffected by TLS either way.

### 7.7 Authentication, permissions and configuration validation

- **v1.9.4 makes a missing/unparseable named config file fatal.** Verified: every unit names an
  existing readable `/etc/turnstone/config.toml`, so this should be a no-op — but it converts a
  warning into a startup failure, so it must be verified per unit.
- `secret://` references are new for `auth.jwt_secret` / `oidc.client_secret`. The live
  `jwt_secret` is a literal value, which remains valid.
- New `files.read` (086) and `files.write` (088) permissions are granted to builtin roles; a
  cluster that had revoked them via role overrides keeps those overrides.
- The Helm changes in v1.9.4 (Kubernetes ≥1.29, JWT secret required, tini PID 1, sidecars) **do not
  apply** — this is a native systemd install, not Helm.

### 7.8 Switchyard compatibility

Switchyard is an **HTTP inference router**; it is not an SDK consumer of Turnstone, so the MCP/Anthropic
SDK bumps do not reach it. The relevant coupling is the `tier1-decision` typed-decision seam (§5.2)
and the `openai-compatible` provider lanes. Both are wire-level and should survive a Turnstone upgrade,
provided the overlay's provider changes are re-applied. The `direct-*` aliases and `server_compat`
payloads must be re-tested after cutover.

> Endpoint hostnames, tailnet addresses and internal DNS names are deliberately omitted from this
> published document; the owner holds them in the host inventory.

### 7.9 Frontend / API compatibility

`admin.js` differs by 1,015 lines and `console/server.py` by 4,628 lines vs v1.9.4. Any custom
console patch (PR #21 at minimum) must be re-applied on the 1.9.4 asset. The console also serves the
web UI from the package, so a venv upgrade replaces the frontend wholesale.

### 7.10 Backup and rollback feasibility

Rollback of the *application* is straightforward: the overlay slots are immutable and `root:root`
(`0555`/`0444`), and each deploy receipt records the exact prior slot. Rolling back means restoring the
previous `PYTHONPATH` drop-in and restarting — **no data operation**.

Rollback of the *database* is the hard part: migrations 077–088 are one-way in practice (080 drops
columns permanently). **Rollback therefore requires a full database restore**, which is available:
nightly `pg_dump` + restic to NFS, verified to contain the dump, with 493 G free.

## 9. Recommended upgrade and alignment strategy

Because the answer to "can we manually update?" is **no**, the recommended path is a **staged
alignment** (classification B). Nothing below should be executed without explicit owner approval.

### Stage 0 — Preserve the baseline

1. Take a **fresh full `pg_dump`** and confirm it in a restic snapshot.
2. Snapshot the overlay slots (`/opt/turnstone-overlays/*`) and all drop-ins to a durable artifact.
3. Record the exact live tree digest of `console-model-form-4254d14f01a4` (the deploy receipts already
   record a slot digest — reuse that mechanism).
4. Export the values migration 080 will destroy (`prompt_templates.activation`, plus a full row dump
   of the 4 skills).

### Stage 1 — Establish a clean 1.9.4 integration branch

1. Create `integration/v1.9.4-<date>` from upstream tag `v1.9.4` (not `main`, not the fork's stale
   base).
2. Add a `remote` for upstream and record the merge base (`28ef63a1`) for three-way analysis.
3. Do **not** start from `fork/main` — it is 436 commits behind and its migration branch is divergent.

### Stage 2 — Reconcile required custom changes

Ordered by risk (highest first):

1. **Port the 4 MCP servers to `MCPServer`** (dockhand, switchyard-ops, openclaw-admin, and the
   truenas/volumio/self-admin trio) — *or* pin them to `mcp<2` in isolated venvs and leave them out of
   the upgrade. **This is the gating item.**
2. **Decide the overlay strategy.** Two viable options:
   - **(a) Re-base the overlay** — re-apply the 25-file delta onto 1.9.4. Highest fidelity, highest
     effort (session.py alone is ~8,300 lines apart).
   - **(b) Rebuild from the fork** — merge `integration/s6-runtime-v187-5427ded` + PR #20 + PR #21
     onto 1.9.4 as Git commits, then regenerate the overlay from the build. Preferred: produces a
     **real commit** and fixes the provenance gap.
3. **Re-anchor the 7 sensor seams** in `session.py` and the typed-decision dispatch in
   `output_guard_judge.py`.
4. **Re-evaluate PR #21** against v1.9.4's own `server_compat` logic — likely retire.
5. **Re-evaluate `_openai_responses.py`** — upstream 1.9.x may already carry the reasoning-replay fix.
6. **Decide on the undeployed fork work** (manual approval, Run Once, storage tooling). Recommend
   **excluding** it from this upgrade; it has never run in production and would multiply the test
   surface.

### Stage 3 — Validate migrations on a disposable database

1. Restore the production dump into a **throwaway** PostgreSQL database (local or a scratch host).
2. Run the 1.9.4 binary against it with migrations enabled.
3. Verify the head lands on `088`, all 12 migrations apply cleanly, and row counts on
   `workstreams`, `conversations`, `prompt_templates`, `model_definitions` match pre/post expectations.
4. **Never** point a 1.9.4 binary at production to "test" migrations.

### Stage 4 — Reproduce the topology in staging

1. Five `turnstone-server` instances (head + 4 nodes) on a staging host, same env shape.
2. One console, one channel gateway, the six MCP adapters.
3. Verify: cluster forms, `/health` agreement, `version_drift=false`, MCP server count, one real
   inference through a `direct-*` alias and through Switchyard.

### Stage 5 — Run the test suites

Upstream v1.9.4 ships 585 test files. Run them against the reconciled tree (note: this host has no
`pytest` in `/opt/turnstone-venv`; the repo suites are standalone `__main__` runners — plan the
runner accordingly). Add the fork's own suites: sensor, typed-decision, judge-audit, approval.

### Stage 6 — Verified rollback checkpoint

1. Confirm the pre-upgrade `pg_dump` restores into a scratch DB and matches row counts.
2. Confirm the previous overlay slot + drop-ins can be restored and the old process starts against
   the **restored** (076) database.
3. Write the rollback procedure as an executable runbook and rehearse it once in staging.

### Stage 7 — Coordinated cutover (owner approval required)

A single maintenance window:

1. Stop all 6 servers + console + channel gateway.
2. Take a final `pg_dump`.
3. Install the new venv + overlay.
4. Start the head; confirm migrations reach 088.
5. Start nodes, console, gateway; confirm cluster health and `version_drift=false`.
6. Smoke-test inference, MCP, judge, typed-decision.
7. Hold the old venv and DB dump for the rollback window.

## 12. Readiness classification

### **B — ALIGNMENT REQUIRED**

**Justification.** A manual update is not feasible because three *independent* hard blockers each
require code work before a 1.9.4 process could start:

1. the overlay's `session.py`/`output_guard_judge.py`/`model_registry.py` are built on APIs that
   v1.9.0 removed (`resume()`) or heavily changed, and
2. the MCP SDK major version removes `FastMCP`, breaking six integrations including the
   self-management bridge, and
3. three dependency majors move (`anthropic`, `mcp`, plus removal of `httpx`).

None of these is a configuration change; all are source changes that must be staged and tested.

It is **not** classification C: the evidence is sufficient and the ambiguities are bounded. The
migration lineage — the largest suspected unknown — is **resolved in production's favour** (stock
076, no custom migrations applied). What remains is ordinary alignment work with a clear sequence.
